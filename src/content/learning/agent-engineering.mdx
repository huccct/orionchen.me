模型提出下一步，应用负责决定是否执行。把一次任务做可靠，需要同时理解上下文、工具、状态、失败和权限。

## 从一次任务开始

建议先沿着 **调用提议与参数校验 → 结果回传与循环边界 → 任务状态与持久化 → 超时与有限重试 → 幂等键与副作用** 探索，再回来看上下文、取消、安全和评测。

每个概念都有使用场景、误区、练习目标与参考资料。地图连线表示知识联系。知识库检索见 [RAG 与知识检索](/learning/rag)，跨会话记忆见 [上下文工程](/learning/context-engineering)。

## 动手推演

任务实验固定为“用户已授权创建一份报告”，可以对比正常成功、参数校验失败、提交后响应超时和提交后取消。超时场景还可以切换是否复用幂等键，观察一次重试为什么可能创建两份报告。

先预测，再逐步观察。特别注意：**超时不代表没有执行，取消不代表撤销，成功响应不代表业务结果正确。**

这是浏览器内的固定教学模型，不调用模型、不连接外部工具、不创建报告，也不模拟真实调度、计费或网络竞态。实验同时展示工具实际副作用和执行器状态，是为了帮助比较两者；真实执行器在响应丢失时不一定知道工具已做了什么。预测与步骤只保留在当前实验视图，离开或刷新后清空。

## 执行架构与版本发布

在「架构与发布」对照固定周报、开放调研和独立复核等任务，比较 Workflow、ReAct 类工具循环、Planner–Executor 与 Multi-Agent。每种方式都要明确谁决定下一步、谁保存任务进度、如何停止，以及如何处理已经发生的写入。

用同一个报告 Agent 演练发布。先发布通过门禁的 v2，观察以 v1 启动的任务仍绑定 v1。再试着发布产生重复报告的 v3，确认新任务仍走 v2。启动并跟踪一项 v2 任务，再回滚到 v1，观察 v2 任务与此后新任务的版本差异。浏览器使用固定门禁结果演练路由，真实的重复写入检查见 [Agent 轨迹评测与回归门禁](/learning/agent-trace-evaluation)。

设计版本清单时，至少记录 Prompt、模型、工具契约、执行策略和评测集版本。发布后从真实运行轨迹筛选坏例，记录失败时绑定的版本并复核预期，再把坏例作为下次发布的回归样本。

## 把地图接回真实项目

接着做 [Agent Runtime：任务租约与断点恢复](/learning/agent-runtime)，用 SQLite 和独立进程复现写入成功后 worker 被杀的场景。

选一个自己做过的任务，标出每次模型请求、工具调用、权限检查和持久化位置。再分别推演：工具执行前失败、执行成功但响应丢失、用户中途停止。给每个失败点写下“已知什么、未知什么、下一步能安全做什么”。

前端反馈可结合 [React 知识地图](/learning/react)，服务端校验、队列和数据边界可结合 [NestJS 知识地图](/learning/nestjs)。这里不假设任何具体产品的内部架构。
