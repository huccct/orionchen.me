Agent 调用工具创建报告。数据库已经提交，worker 却在保存任务结果前被杀掉。下一次执行要同时解决两个问题：**什么时候可以接管任务？怎样拿回报告结果而不重复创建？**

## 先预测，再运行

实验从一个待执行任务开始。Worker A 领取任务，获得截至 `t=10` 的租约。它提交报告后收到 `SIGKILL`，任务结果还没写回。Worker B 分别在 `t=9` 和 `t=10` 尝试领取。

先预测三个时点的任务状态和报告数量：A 被杀后、B 第一次尝试后、B 第二次尝试后。

在 macOS 或 Linux 下载脚本，进入下载目录，用 Python 3 运行。脚本用标准库创建临时 SQLite 数据库，每次运行都会从空库开始。

<a href="/learning/experiments/agent-runtime.py" download>下载实验脚本 agent-runtime.py</a>

```bash
python3 agent-runtime.py
```

## 对照数据库里的结果

1. **A 被杀后**：报告已提交，任务仍是 `running`，第 1 次执行还没有记录结果。
2. **B 在 t=9 尝试**：租约仍有效，领取语句没有更新任何行。
3. **B 在 t=10 接管**：领取语句把执行次数推进到 2。工具用同一个操作键找到原报告，任务记录写回同一个报告 ID。最终任务是 `succeeded`，报告仍只有一份。

脚本用独立进程、真实的进程退出和 SQLite 提交验证这三个时点。实验用手动推进的时钟复现租约边界。任务与报告共用一个 SQLite 文件，各自提交事务，借此保留「业务写入已成功、任务记录还没更新」的故障窗口。

## 找到三个各管一件事的机制

- **租约决定谁能接管。** 领取用一条带条件的 `UPDATE`。租约到期后，新的执行才能领取任务。
- **执行次数约束谁能写回任务。** 写回时核对当前执行次数与租约。旧 worker 即使在新 worker 接管后恢复运行，也无法提交旧任务结果。
- **业务操作键约束工具的副作用。** 同一个任务步骤在两次执行中使用相同操作键。报告表的唯一约束负责去重，工具再读取已存在的报告 ID。真实工具若跨服务写入，由接收写入的服务落实这个契约。

## 注入一次重复写入

运行 `python3 agent-runtime.py --duplicate-report`。这个参数把执行次数拼进操作键，模拟把每次执行的 ID 误用成业务幂等键。第 2 次执行会创建第二份报告，回归检查会指出是哪次工具调用导致的。接着做 [Agent 轨迹评测与回归门禁](/learning/agent-trace-evaluation)，对照正常和故障轨迹。

这个实验只推进一个工具步骤。对于包含人工审批的任务，可以把等待审批设计成可持久化的业务状态，收到审批事件后再领取执行。对需要长时间占用 worker 的步骤，还要设计续租，并在实际并发和故障下验证。
